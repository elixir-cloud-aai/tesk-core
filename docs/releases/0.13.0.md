tesk-core 0.13.0 gives the filers and the executors resource limits, so that namespaces with a `ResourceQuota` on `limits.cpu` or `limits.memory` (e.g., those of the CERIT-SC cluster) accept the filers' pods and every executor that requests the resources under quota (`cpu_cores` for `limits.cpu`, `ram_gb` for `limits.memory`); executors without such a request still need a default limit from a `LimitRange`. It also fixes executors with `cpu_cores` and `ram_gb` that never started in namespaces with a default memory limit below their `ram_gb`, and tasks whose pods Kubernetes refuses to create no longer stay `RUNNING` for ever. **Operators must act on one behaviour change**: `ram_gb` is now a hard memory limit also for tasks that set `cpu_cores`, so executors that use more memory are stopped (`OOMKilled`). The filers' new default resources may need `FILER_RESOURCES` in namespaces with a strict `LimitRange`, and the taskmaster needs a new permission, `list` on `events`, to end tasks with refused pods at once. Read the [upgrade notes for 0.13.0](https://tesk.readthedocs.io/en/latest/tesk-core/upgrading/#0130) before you upgrade.

## Breaking changes

- `ram_gb` is a hard memory limit for executors that also set `cpu_cores`, as it already was for tasks that set only `ram_gb`: an executor gets a limit for each resource that it requests without one, so a task that uses more memory than its `ram_gb` now ends with `EXECUTOR_ERROR` (`OOMKilled`) instead of completing (#160, #164)

## Features

- The filers' pods have resource requests (100m CPU, 128Mi memory) and limits (1 CPU, 512Mi memory) by default, so that namespaces with a quota on limits accept them; `FILER_RESOURCES` still replaces them (`{}` for none) and now refuses resources that a container can't have, invalid quantities and requests above their limits, with an error in the taskmaster's log, keeping the default (#163, #164)

## Fixes

- Executors with `cpu_cores` and `ram_gb` above a namespace's default memory limit start again, instead of leaving their task running for ever with an invalid pod (#160, #164)
- A task whose pod Kubernetes refuses to create ends: the taskmaster reads the job's `FailedCreate` events and ends the task at once with `SYSTEM_ERROR` and Kubernetes' message when waiting can't help, and otherwise (e.g. a used-up quota) waits up to `TESK_MAX_QUEUE_SECONDS`, if set. This needs `list` on `events` in the tasks' namespace; without it, the taskmaster logs a warning and relies on `TESK_MAX_QUEUE_SECONDS` alone (#169, #170)
